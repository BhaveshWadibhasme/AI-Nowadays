Tools + agents

Tool calling MCP Agent loops Multi-agent Workflows

A tool call is a structured request. Your code performs it and returns the result. An agent is a loop that lets the model choose the next tool until it stops, inside a harness you wrote: state, permissions, a budget, a trace, and a stop. Most business processes are not that loop. They are a workflow you can draw. The skill is knowing which one you are building, and refusing the other when a client asks for “an agent” by name.

Why it matters in production

Tools are where a language model touches a system of record. That is the step that sends the email, files the ticket, or reads a balance. The four pillars before this one exist so that step is narrow: the model saw only what it should, the loop cannot spend without a cap, you can tell when a change made it worse, and a side effect waits for a check. Skip those and an agent demo becomes an incident with a transcript.

The other failure is architectural. A team reaches for a multi-agent crew to do five steps they could have written down. The crew is slower, harder to eval, and impossible to explain when it skips a step. Forward-deployed work is mostly the opposite move: turn an “agent” request into a graph you can test node by node, and keep a real loop only where the next action depends on something you could not know up front.

Why it matters

Ask which steps are known before the user speaks, and which steps depend on a result you will only have after a tool returns. Draw the first set. Put a loop, with a budget, only on the second. If you cannot draw it, you are not ready to pick a framework.

Core techniques

Tool calling

The contract is the schema and the description

Function calling, as OpenAI and Claude document it, is the model emitting a structured call that your process executes. The schema is the contract: names, types, enums, and which fields are required. The description is how the model chooses among tools. Vague descriptions produce wrong calls. Overlapping tools produce arbitrary calls. Too many tools in one prompt produce a model that picks one it half-remembers. Anthropic’s note on writing tools for agents is the piece to give the engineer who is about to add twelve functions. Validate arguments in your code before anything with a side effect runs. That check is the guardrails pillar, applied at the only moment it counts.

MCP

One way to expose tools, not a reason to trust them

The Model Context Protocol is an open protocol for exposing tools and resources to a host. It earns its place when the same capability must work across more than one agent client: an IDE, a desktop app, a product you are building. It does not make a tool safe, and it does not review the server for you. A server you did not read is still code, often holding credentials. Pin versions, run it where you can see its egress, and give it the same least privilege you would give any other integration. “It speaks MCP” is a compatibility statement. It is not a security review.

The harness

The loop is the small part

The harness is the software around the model: state, the allowed tools, retries, timeouts, token and money budgets, tracing, and the condition that stops the loop. LangGraph is the explicit version. You draw the control flow, and the model fills specific nodes. That is usually what you want on a client site, because you can point at a node and say what it is allowed to do. A free loop, where the model picks any tool until it feels done, is justified when the path depends on intermediate results you cannot script. Give it a maximum number of steps, a maximum spend, and a trace of every call. An unbounded loop is an unbounded incident.

Multi-agent

Split roles to enforce a boundary

Separate agents when you need a fresh context or a real split of tools and permissions. A reviewer who should not see the drafter’s scratchpad is a reason. A researcher whose only tool is search, and a publisher whose tool can send, is a reason. A crew of agents that share the same tools and the same goal is usually a slower way to write one prompt. CrewAI is organised around role-based crews. LangGraph can host the same split as nodes with different tool sets. Use the split to enforce a boundary you can name. An org chart made of prompts is not a boundary.

Workflows

When not to use an agent

Classification, extraction, a single retrieval plus an answer, a form, and a business process with known branches are pipelines. Write them as a workflow: a graph you control, with a model inside the nodes that need language. They are cheaper, they are easier to evaluate node by node, and when they fail you can say which step failed. Anthropic’s “Building effective agents” draws this line between workflows and agents, and LangGraph’s workflows-and-agents page is the matching engineering note. Reach for an agent loop only after you can say which decision cannot be written down in advance. If you can write it down, write it down.

Side effects

The loop proposes, the harness commits

Reads can sit inside the loop. Writes wait. The harness turns a proposed action into a real one only after the guardrail checks: schema, permission, and, for send, pay, delete, file, or publish, an approval. Make the tool idempotent where a retry would double the effect. Log the call, the arguments, and the result onto the same trace the measure pillar scores. A framework that commits inside the model process, where your approval cannot intercept, is the wrong framework for that action.

Watch-outs

Common pitfalls

  • Agent as the default architecture. The client said the word. The work was a five-step process. You now have a loop you cannot eval.
  • Tools with overlapping descriptions. The model picks one. You cannot say why. Support cannot either.
  • A dozen tools in one prompt. Choice quality drops as the menu grows. Split the menu by step.
  • No step cap, no spend cap, no timeout. The loop is a while-true with a credit card.
  • Side effects inside the loop. A retry sends the email twice. Approval never had a place to stand.
  • Multi-agent as an org chart. Five personas, one shared toolbox, no boundary. You paid for orchestration and got a group chat.
  • MCP as a trust mark. The protocol is a connector. The server is still code with credentials.

Design review

Practical checklist

  • List the steps you can draw before the user speaks. Those are a workflow.
  • Name the decision that depends on a tool result you cannot predict. That is the only candidate for a loop.
  • Give each tool a schema, a one-job description, and a permission scope.
  • Remove overlapping tools. Split read from write.
  • Validate arguments in your code before a side effect.
  • Cap steps, tokens, spend, and wall-clock time on every loop.
  • Trace every call: name, arguments, result, latency, and the model that chose it.
  • Put approval in front of send, pay, delete, file, and publish.
  • Make side-effecting tools idempotent under retry.
  • If you adopt MCP, review the server, pin it, and scope its credentials. Do not treat the protocol as a review.

Key tools and frameworks

LangGraph

Explicit graphs: nodes, edges, and state you can draw for a client. This is the default harness when the delivery has to be explained and tested. The workflows-and-agents page is the short version of “put the model in a node, keep the control flow in the graph”.

LangChain

The integration layer around model calls and tools. Use it for the adapters. Do not let it become an excuse to skip the graph. If the control flow is implicit, you will not be able to point at the step that failed.

CrewAI

Role-based crews: agents with goals and tools, orchestrated as a group. Reach for it when a real role split is the design, and be ready to justify why those roles do not collapse into one graph with two nodes.

MCP

The protocol to use when a tool must be portable across hosts. Read the introduction, then review the specific server you are about to run. Portability and trust are different questions.
