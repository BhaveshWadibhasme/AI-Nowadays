Measure it

Evals Tracing LLM-as-judge Faithfulness Regression

Measurement is how you know a change helped. Offline evals score a frozen set before you ship. Online evals score a sample of what real users just did. Tracing is the record that makes either score explainable: the prompt, the retrieved ids, the tool calls, the model, the tokens, the latency, and the answer. Without that record, a number is a mood.

Why it matters in production

Prompt, model, index, and tool changes all ship as “small”. The failure mode is a Tuesday where answers got smoother and less true, or a model alias moved under you and the cheap route started failing a schema. The team notices through a client email, because nothing in the pipeline was allowed to say no.

A consultant’s job here is to make the disagreement visible before the go-live. Someone who knows the domain owns a small set of cases. A trace exists for every case. A score is tied to a rubric a second person can apply. Cost and latency are on the same row as quality, so a “win” that doubled the invoice is not recorded as a win.

Why it matters

Ask who can mark an answer wrong, which slice must not regress, and where the trace will live. If the answer is “we’ll look at a few chats”, you do not have an eval. You have a hope that the next reader is careful.

Core techniques

Offline

A golden set with an owner

A golden set is a small, versioned collection of inputs and what “good” means for each one. Good might be a fact that must appear, a source that must be cited, a tool that must be called, or a refusal. Cover the happy path, the edge, the contradiction in the corpus, and the question the corpus does not answer. The owner is a person who knows the domain, not the engineer who wrote the prompt. If the set only contains the demo questions, it will certify the demo. OpenAI’s evals guide and cookbook walk through running a set against a model; the discipline is the same whatever runs the harness.

Online

Sample production, on a schedule

Offline sets go stale. The corpus changes, the questions change, and a model name can point at a new snapshot. Sample production traces and score a slice on a cadence you will actually keep. Watch the slices: language, tenant, intent, and the “not in the documents” bucket. An average that stays flat while one product line collapses is the usual chart. Anthropic’s engineering note on evals for agents is the piece to read before you design an online review for a loop rather than a single completion. Online review also has a privacy constraint: the trace store is a place customer text goes. Decide that before you turn sampling on. That decision belongs with the guardrails pillar.

Traces

The score has to open

Every scored run should open onto the prompt, the retrieved ids, the tool names and arguments, the model, token counts, latency, and the final answer. LangSmith is the tracing and eval product in the LangChain stack. You can trace without LangChain. You cannot debug a faithfulness failure from a single aggregate. When a regression fires, the first click is the trace, not the prompt diff.

LLM-as-judge

Useful at volume, biased, and not the only gate

A model can grade outputs against a rubric when you have more traces than reviewers. It is not a neutral instrument. Judges prefer some styles, they reward length, and a model grading its own family is a poor court. Calibrate the judge on a human-labeled slice before a movement in the judge’s score is allowed to block or bless a release. G-Eval is one published method for rubric grading with a model. Hamel Husain’s guide to LLM-as-a-judge is the practitioner write-up to hand a team that is about to automate the review. Keep a human gate on the release even after the judge is calibrated. Change the judge and the system in different weeks, or you will not know which one moved.

What to score

Name the question the metric answers

Teams use faithfulness and groundedness for the same question: do the claims in the answer stick to the sources you gave the model? Ragas defines a faithfulness metric in those terms, and the paper is the reference for the suite around it. Context precision and context recall ask a different question: did you retrieve the right passages, and did you miss the one that was needed? Answer relevance asks whether the response addresses the question. Task success asks whether the workflow finished the job, including tool side effects. Refusal correctness asks whether it refused what it should and answered what it should. Cost and latency sit beside these, because a perfect answer that misses the latency budget is a product failure. Pick the few metrics that match the failure you are afraid of. A dashboard of twelve scores that nobody owns will not stop a release.

Regression

The golden set runs when the system changes

Run the set when prompts, models, chunking, indexes, or tools change. A drop on a named slice blocks the change. Wire it like any other test: same command, same threshold, a human who can waive it with a reason. Batch APIs are the right place to run a large offline set so the eval itself is not the expensive part of the week. The cost primer covers that tier. The eval harness is part of the application, not a notebook someone reruns before a big demo.

Error analysis

Read the failures

A metric you have not checked against real traces is a number. Read a handful of failures every cycle and write down the actual mode: wrong chunk, right chunk ignored, tool called with a bad id, refusal missing, tone wrong. That note is what you take back to context, cost, guardrails, or tools. Hamel Husain’s “Your AI Product Needs Evals” is the essay that argues for this loop in product language. Hand it to the team, then do the loop. Do not treat the essay as a substitute for the set.

Watch-outs

Common pitfalls

  • One average. It hides the slice that broke. Report the slice you are afraid of, by name.
  • A golden set cloned from the demo script. It will pass on the day you most need it to fail.
  • A judge that rewards polish. Longer, more confident answers win. Calibrate against people who know the domain.
  • The judge and the system changed together. You cannot tell which movement is real.
  • No trace behind the point. The score dropped and nobody can open the prompt. The eval is not operational.
  • Production text copied into a third-party trace tool with no decision. Sampling is a data flow. Treat it as one.
  • Metrics with no owner. Twelve charts, no one who can mark an answer wrong, no release gate.

Design review

Practical checklist

  • Name the failure you are afraid of, and the metric that would catch it.
  • Give the golden set an owner who can mark an answer wrong.
  • Include refusals, missing-from-corpus cases, and at least one contradiction.
  • Version the set. Change it on purpose, in its own commit.
  • Trace prompt, retrieval ids, tools, model, tokens, latency, and answer.
  • Decide where production traces are stored before you sample them.
  • Calibrate any LLM judge on a human-labeled slice. Keep a human on the release.
  • Run the set on prompt, model, index, and tool changes. A named slice can block.
  • Read failures each cycle and file the cause under the pillar that can fix it.
  • Put cost and latency next to quality so a slower, pricier “improvement” is visible.

Key tools and frameworks

LangSmith

Tracing plus evaluation in the LangChain stack. Use it when the app is already on LangChain or LangGraph and you want runs, datasets, and scores in one place. The observability and evaluation docs are separate on purpose: a trace you never score, and a score you cannot open, are both incomplete.

Ragas

A library aimed at RAG evaluation, with faithfulness as a first-class metric: are the claims supported by the retrieved context? Start there when the product is question-answering over documents. Read the metric page so the team means the same thing by the word.

DeepEval

An eval framework with its own metric set, including faithfulness, and a shape that fits into test runs. Useful when you want the check to live next to the rest of the test suite.

OpenAI Evals

The platform guide and the cookbook example are enough to run a first set against their API. The harness can be theirs or yours. The set and the rubric are yours either way.
