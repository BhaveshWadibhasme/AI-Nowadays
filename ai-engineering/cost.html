Cut down the cost

Routing Caching Distillation Batching Quantisation

Cost work starts after you know which call is expensive, and it stops when the cheaper path still passes the eval. The levers are familiar: send the turn to a smaller model, cache the part of the prompt that does not change, batch the work that can wait, and, if you host the weights, serve them in a lower precision. Latency sits on the same dial. A saving that makes the interactive path unusable is not a saving the client will keep.

Why it matters in production

Pilots are priced like a handful of enthusiastic users. Production is priced like every ticket, every retry, and every tool round-trip. The bill concentrates in a few shapes: a long system prompt resent on every turn, a reasoning model used to classify a yes-or-no, a retrieval blob that grew because nobody set a budget, an agent loop with no step cap. Context engineering decides what is worth sending. This pillar decides how you pay for it, and how long the user waits.

Consultants get called when finance sees the invoice, or when the team has already “optimised” by swapping in a smaller model and quality fell on the one slice the client cares about. Both conversations go better if you can point at tokens in, tokens out, cache behaviour, and the eval that guards the change.

Why it matters

Ask which request sits on the user path, what it costs today, and what latency the surface can tolerate. Then ask which workload can wait an hour. Those two lists are the design. A single “make it cheaper” goal, with no slice and no budget, produces a cheaper demo and an angrier production.

Core techniques

Measure first

Name the call that dominates

Log model name, input tokens, output tokens, cache hit or miss, latency, feature, and tenant. Optimise the call that dominates the bill or the wait, not the one that is easiest to rewrite. A routing layer in front of a prompt you have never measured just hides the spend. This is the same trace the measure pillar wants; cost is one of the fields on it, not a separate dashboard you build later.

Routing

A sufficient model, not a famous one

Classify the turn and send it to a model that can do that turn. Extraction, routing, and short classification often belong on a small model or even a rule. Open-ended drafting and hard judgment stay on a stronger model. Keep a fallback: if the cheap model fails schema validation or abstains, escalate. Write the routing rules down so support can explain why two users saw different behaviour. OpenAI’s model selection guide and Claude’s model overview are the vendor pages for choosing among their own models; the pattern is the same if you mix providers.

Prompt caching

Stable prefix, variable suffix

Prompt caching, as OpenAI and Anthropic document it, reuses a repeated prefix of the prompt so a later request with the same beginning does less work. Design the prompt so the stable part comes first: system instructions, tool definitions, a large document that does not change within the session. Put the user message, the timestamp, and anything personal at the end. A clock or a request id inside the system prompt will quietly destroy the hit. Prompt caching is not a response cache. It does not reuse the answer. It reuses the work of reading the prefix.

Answer caches

Cache the response only inside a scope

An exact cache is reasonable for identical requests: same model, same prompt, same tools, and a question that is not personal. A semantic cache, which serves a previous answer for a nearby embedding, is where teams get hurt. Two questions can sit next to each other in vector space and differ by a name, a number, or a permission. If you cache across users, the cache key has to include the authorization scope, or you will leak one customer’s answer to another. Expire anything that depends on a corpus you reindex.

Smaller models

Distil a narrow task, then re-check it

Once a strong model has defined the behaviour on a narrow task, a smaller model fine-tuned on those examples can take that task over. OpenAI documents this under supervised fine-tuning, including distillation from a larger model. The narrow task needs its own eval. Distillation does not transfer open-ended judgment, and a small model that was “pretty close” on the demo set will miss the slice you forgot to label. Use the strong model as the teacher and as the escalation path, not as something you turn off on day one.

Batch and defer

Interactive prices are for interactive work

Evals, backfills, nightly enrichment, and bulk re-scoring do not belong on the synchronous user path. OpenAI’s Batch API and Flex processing, and Claude’s batch processing, are the documented ways to submit work that can wait. Use them for the measure pillar’s offline runs as well as for data jobs. Do not point a user-facing button at a batch queue and call it latency optimisation.

Quantisation

When you host the weights

If you serve your own model, reduced precision is how you fit it and how you raise throughput. vLLM and Hugging Face document the methods, including int8 and int4-style quantisation. Treat the quantised model as a different model. Run the same golden set you trust for the full-precision one, and read the slices, not the average. A model that was already borderline on groundedness will fail those slices first. Quantisation is not a lever on a hosted API where you do not hold the weights; there you route, cache, and shorten.

Latency

Write a budget per surface

Streaming, a lower max output, fewer tool rounds, a smaller model, and a cache hit all move wait and spend, often in opposite directions. Chat has a latency budget. An overnight reconciliation does not. OpenAI’s latency guide is the practical list for API calls: what you can shorten without changing the product. Cost work that makes the interactive path slower than the budget is a failed optimisation, even if the invoice dropped. Speculative decoding and other serving tricks, when you self-host, belong in the same review: they are latency tools, and they still need the eval.

Watch-outs

Common pitfalls

  • Optimising before the trace exists. You will tune the prompt you can see and miss the retry loop that runs five times.
  • A timestamp in the cached prefix. The prefix is no longer stable, the hit rate collapses, and the dashboard still says caching is “on”.
  • A semantic cache with no tenant in the key. Nearby questions are not the same question, and they are not the same user’s data.
  • Distilling without a slice eval. The small model matches the teacher on the happy path and fails on the refusal, the number, or the rare product.
  • Quantising a model that was already close to the line. The average score moves a little. The slice the client will demo moves a lot.
  • Batch endpoints on the user path. The API will accept the call. The product will feel broken.
  • Routing you cannot explain. If support cannot say why this ticket used the cheap model, the router is an incident waiting for a screenshot.

Design review

Practical checklist

  • Log tokens, model, latency, feature, and tenant for every model call.
  • Separate the user path from work that can wait an hour or a night.
  • Write a latency budget per surface before you chase a cheaper model.
  • Put stable instructions and tools first if you rely on prompt caching. Keep clocks and user text at the end.
  • Key any answer cache by authorization scope, and expire it when the corpus changes.
  • Route by task. Escalate when the cheap model fails the schema or abstains.
  • Distil only a named task, and gate the swap on that task’s eval.
  • Send evals, backfills, and re-scores through a batch or deferred tier.
  • If you self-host, re-run the golden set on the quantised build and read the slices.
  • Cap steps, output tokens, and spend on any loop. An uncapped agent is an uncapped invoice.

Key tools and frameworks

Provider controls

Prompt caching, batch, flex, and model choice are features of the API, not of your framework. Read the OpenAI and Claude guides before you wrap them. A framework that hides the prefix will also hide the cache hit.

vLLM

The usual open serving stack when you host weights. Its quantisation docs are the checklist for reduced-precision serving, and the server is where cache-aware batching of concurrent requests actually happens.

Hugging Face

Transformers documents quantisation of the model object itself. Text Generation Inference documents quantisation from the serving side. Use whichever matches where you run the weights, and keep the eval harness pointed at the build you deploy.

LangSmith, or any trace store

You cannot route or cache with intent until a trace shows the expensive call. LangSmith is the LangChain-native place those fields live. The requirement is the fields, not the vendor. See the measure primer for how the trace earns its keep.
