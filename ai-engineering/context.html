Give it context

RAG Retrieval Memory Chunking Long context

Context engineering is the work of deciding what the model sees on this request: which sources, in what order, under whose permissions, and with what evidence a person can check. Most production failures that get blamed on “the model” are failures of that assembly. The model answered from the wrong document, from a stale policy, from a chunk that cut a table in half, or from a prompt so crowded that the question was the least visible thing in it.

Why it matters in production

A demo retrieves three PDFs the team uploaded that morning. A deployment retrieves a corpus with owners, retention rules, contradictory versions, and access control. The quality of the answer tracks that assembly more closely than it tracks the model name on the invoice. Clients describe the symptom as hallucination. Often the retrieved text never contained the fact, contained two conflicting facts, or contained the fact in a form the chunker destroyed.

You cannot evaluate your way out of a corpus you have not inventoried. Measurement, the third pillar, tells you the answer is wrong. Context is where you fix the cause. Cost, the second pillar, is why you do not paste the entire corpus into every call just because a window got larger.

Why it matters

Before you discuss models, ask what the system is allowed to treat as true, who is allowed to see each source, and how a reviewer jumps from a sentence in the answer to the span that supports it. If nobody owns that, you are still in a demo.

Core techniques

Retrieval

Search at question time

Retrieval-augmented generation searches an index when the question arrives and places the hits in the prompt. Use it when the corpus is larger than the window, when it changes, or when different users must see different documents. Hybrid retrieval matters: lexical search such as BM25 finds product codes, clause numbers, and error strings, while embeddings find paraphrases. Neither covers both. A question rewrite step, before the search, is how you handle multi-part questions and follow-ups that say “and the other one?”.

Chunking

Split on the document, not on a round token count

Split on structure first: headings, tables, lists, code blocks, slides. A fixed token window with overlap is a fallback, not a design. If a procedure has six steps, a chunk that holds steps four through six and none of the condition is a wrong answer waiting to happen. Keep a stable id for the source, the section, and the version, so you can cite a span and delete it when the policy changes. Anthropic’s contextual retrieval pattern is the extra step of attaching a short explanation to each chunk before you embed it, so a paragraph that only says “this increases next year” still says what “this” is once it is out of the page.

Reranking

Retrieve wide, then read the short list

First-stage retrieval should be wide and cheap. A reranker then reads the question beside a few dozen candidates and orders them by relevance to that question. This is where precision is won for high-stakes answers, and it is an extra call, so it belongs on the path where being right matters more than shaving a little latency. Cohere documents a rerank model; the pattern is the same if you host a cross-encoder yourself. Do not use the same top-k for “what is the holiday calendar?” and “does clause 14.2 survive the amendment?”.

Assembly

Write a budget, then an order

The context is not one blob. Instructions, tool definitions, retrieved passages, memory, and the user message compete for one window. Write the budget down: tokens for the system prompt, tokens for tools, tokens for evidence, tokens for history. Put the evidence next to the question. Do not bury the instruction or the question in the middle of a long paste. The paper Lost in the Middle is the reference for why position is a design choice: models do not use a long input evenly. A fact you care about should be placed, not hoped for.

Memory

Three stores, three rules

Conversation history is short-term memory. A store of confirmed preferences or past decisions is long-term memory. The corpus of policies and documents is knowledge. Mixing them is how a guess from last Tuesday becomes a fact in next Tuesday’s prompt. Write memory back only after a person or a validator has confirmed it. Retrieve memory with its own step and its own permission check. A chat transcript is not a knowledge base, and a knowledge base is not a place to store “the user seemed to prefer the blue plan”.

Long context

A larger window is a trade

A long context window lets you skip retrieval for a small, stable packet you have already decided is in scope: one contract, a slice of a repo, a thread. It costs more, it is slower, and the model still does not attend to every token equally. It does not solve freshness, and it does not solve permissions. You should not paste another tenant’s documents into the window because they fit. Retrieval stays the default when the corpus grows, changes, or is access-controlled. Use the long window for the packet that survived that decision. Claude’s context-window guide, and the prompt-engineering notes from both Claude and OpenAI, are the vendor pages to read before you spend the tokens on a long paste.

Citations

The answer has to point at a span

If the user cannot see which source supported a claim, your experts cannot trust it and your evals cannot check it. Require the answer to carry source ids that exist in the retrieved set. Anthropic’s citations API and an ordinary instruction to quote a chunk id are two versions of the same contract. An answer with no supporting span, on a question that required evidence, is an abstention or a flagged draft. It is not a silent success. This is also how the measure pillar gets a faithfulness check: you can only score groundedness if the sources were actually in the prompt.

Watch-outs

Common pitfalls

  • The window as a junk drawer. A larger context window is not a corpus strategy. Stuffing “everything we have” raises cost, hides the question, and still misses the document that was updated this morning.
  • Embeddings alone. SKUs, error codes, clause numbers, and names fail fuzzy search. If the business talks in identifiers, you need a lexical path.
  • Chunks that break the unit of meaning. Tables split down the middle, definitions separated from the term, steps separated from the condition. Inspect real chunks against real questions before you tune the embedding model.
  • Authorization after the model has already read the text. Filtering the answer is too late. The permission check belongs in the query, so another tenant’s paragraph never enters the prompt.
  • An index nobody owns. No recrawl, no delete path, no version. Yesterday’s answer cannot be explained, and a removed policy is still retrievable.
  • Memory that writes guesses back. The model’s summary of the user becomes the next prompt’s fact. Confirm before you store.
  • Uncited fluency. The prose sounds grounded because it is smooth. Without a span, you do not know whether it is.

Design review

Practical checklist

  • Inventory the sources: system of record, owner, freshness, and who may read each one.
  • For this task, decide what is retrieved, what is pinned in the prompt, and what is memory.
  • Chunk by document structure. Read a sample of chunks next to real questions.
  • Use hybrid retrieval wherever identifiers and exact phrases carry the meaning.
  • Rerank when the cost of a wrong passage is higher than the cost of the extra call.
  • Apply authorization in the retrieval query, before text reaches the model.
  • Require citations that resolve to ids in the retrieved set.
  • Write a token budget for instructions, tools, evidence, and history.
  • Version the index with the corpus so you can explain yesterday’s answer.
  • Define the abstain path for empty retrieval and for sources that contradict each other.

Key tools and frameworks

LlamaIndex

The framework to reach for when the problem really is a corpus: loaders, node parsers that respect structure, indexes, and query engines. Its RAG guide is the cleanest single introduction to the pattern.

LangChain and LangGraph

LangChain is the integration layer: loaders, splitters, retrievers, and the glue into the rest of the app. LangGraph is what you want when assembly is a process you must explain: rewrite the query, retrieve, rerank, then answer, with state you can trace. LangChain’s current RAG write-up lives under Deep Agents; read it as their retrieval guide, and use LangGraph when the control flow should be explicit.

pgvector

A common way to keep vectors beside the relational rows you already govern. Useful when the permission model already lives in Postgres and you do not want a second store with a second access story.

A reranker

Cohere’s rerank docs are a clear description of the second-stage call. The component matters more than the vendor: something that scores query-and-passage together after a wide first pass.
