Harness²: letting agents edit their own harness, a use-case guide

FrameworksAgentsEnterprise

Google Research's Harness² lets a coding or office agent improve its own harness on each new task, with no answer key. For each task it runs the unedited harness, tests two edited ones (a generic fix and a domain fix), composes what the evidence supports, and stores lessons for later tasks. In the paper, Gemini 3.5 Flash under OpenCode rose from 72.4 to 77.5 on WorkBuddy-Bench in one step. This guide covers how it works, an enterprise scenario, a safe pilot, and where it falls short.

Basics

What a harness is

A harness is the system around a model that lets it act as an agent: prompts, tools, memory, skills and orchestration. The Harness² README says exactly that, and calls the process of optimising it harnessing. The paper writes it as Agent = Model + Harness, with the model weights frozen.

Harness² exposes eight editable components, each mounted as a file in the runtime: system prompt (systemprompt.md), guardrails (guardrails.md), memory (LongTermMEMORY.md), skills (skills/<n>/SKILL.md), tool guidance (tool_guidance.md), scripts (scripts/<name>.py), subagents (sub_agents/<n>/AGENT.md) and a middleware plugin (plugin/<name>.ts). The paper groups them by role: context construction, tool interface, orchestration and middleware.

Why you should care: Epoch AI reports that on SWE-bench Verified, simply switching the scaffold makes up to an 11% difference for GPT-5 and up to 15% for Kimi K2 Thinking, and calls scaffold choice the single biggest impact on the overall score. The scaffold is not packaging. It is a large part of the result.

Why it matters

When you hand a client an agent, you are shipping a model plus a harness. The harness is the part you can actually tune on site, and it is where much of the variance sits.

Method

How Harness² works, step by step

Harness² couples two levels of recursion. The task-level step has no ground-truth verifier. It runs on a single task the agent has never seen.

  1. Reference run. The agent runs the task with the current (base) harness. The paper stresses this shows how the harness behaves, not whether the answer is right.
  2. Propose. A harness editor reads the task, harness, reference run, earlier history and the improvement library, then drafts two candidates: an invariant one aimed at generic agent weaknesses (planning, tool use, context management, delegation) and a domain one aimed at the knowledge, procedures and constraints of the current domain or environment. Each candidate is an executable harness made by editing the component files.
  3. Probe. Each candidate runs on the same task under matched model and environment settings. Comparing trajectory and deliverable with the reference gives a behavioural contrast: did the edit fix the targeted deficiency, change nothing, or cause a regression? The paper says these contrasts inform composition and do not verify correctness.
  4. Compose. A composer reads the reference, candidates, diffs and evidence and builds the successor harness. It may merge supported changes, revise conflicts, adopt one candidate or keep the current harness. Each decision is tied to an observation. The composed harness then runs to produce the final deliverable.
  5. Reflect (harnessing-level recursion). After the task, an experience reflector stores the adopted harness and evidence-supported lessons in a per-domain library. Later tasks in that domain read it. Per the experiments guide, tasks within a domain run in order and read only earlier entries, and libraries are separated by benchmark, executor, mode, budget and seed.

Scaling knob k. --k 1 is one Propose–Probe–Compose step. In parallel mode, k general and k domain candidates are probed and k compositions produced. In sequential mode the refined harness and evidence are carried through k successive steps. The default executor is OpenCode; --substrate cx switches to Codex.

Where the "judge" fits. The LinkedIn summary describes a model judge keeping edits. In the paper this is the Compose step, which decides from behavioural evidence and model judgment. The separate harness2-judge command in the repo is a benchmark scorer. Its source docstring says it measures the chosen run after selection and that nothing in the method imports it.

Why it matters

The design bet is that you can improve an agent on a new task without knowing the right answer, by comparing how differently-edited versions behave on that same task.

Repo tour

Code structure at a glance

The repo is Apache-2.0 Python (Linux, Python 3.12, uv). The directories I read in the file tree:

  • harness2/core/: the method. Includes proposer.py, recursion.py, library.py (per-domain experience library), selection.py, judge.py, ledger.py, spec.py and tree.py.
  • harness2/substrate/: executor adapters, opencode.py and codex.py.
  • harness2/benchmarks/: adapters for JobBench, LAB and WorkBuddy-Bench.
  • harness2/cli/: harness2, harness2-setup, harness2-check, harness2-judge, harness2-report, harness2-demo and harness2-bridge.
  • third_party/: runner overlays and patches for the upstream benchmarks; docs/: SETUP, BENCHMARKS, EXPERIMENTS.

Per library.py, each adopted harness is stored as a full tree plus an EXPERIENCE.md with cue, lesson and evidence, and "the whole tree is carried, never a summary".

You can try it with no credentials: harness2-demo --output runs/demo --k 2 runs both recursion modes with deterministic editors and real Python executions.

Why it matters

It is a research harness built around three benchmarks, not a drop-in product. Expect to write your own task adapter for a client environment.

The control that matters. Directly refining the base harness without reference executions, probes or the library degraded WorkBuddy Code from 73.4 to 63.2 and Web from 69.9 to 65.0. That is the "blind rewrite" number in the LinkedIn post (my mapping of that label to the paper's "Direct Editing w/o Execution"). A library built at k=1 restored base performance; at k=5 it supported gains of 0.9, 4.4 and 5.1 points on Code, Web and Office.

Worked case from the paper. A JobBench task scored 43.1 at baseline. The trajectory showed procedural failures, not knowledge gaps: figures never reconciled across source files, and outputs never reopened after writing. The invariant edit added a guardrail to inventory inputs, trace figures to sources and run a verification script; the domain edit added a reconciliation skill and number-format tool guidance. The composer kept all four edits and the re-run scored 77.8.

Cost. The paper says both evaluated configurations sit on the compute–performance Pareto frontier (execution plus improvement tokens counted), and that Meta-Harness used more compute than Harness² at k=5 for lower performance. It also says refinement adds inference cost and the budget range tested is bounded.

Why it matters

Most of the gain came from process fixes (verify, reconcile, inventory inputs) rather than new knowledge. That is the kind of failure that shows up again and again in client work.

Worked example

Enterprise use case: adapting an analytics agent to a client environment

Illustrative scenario, not from the paper. You are an FDE dropped into a client with an agent (OpenCode or Codex) that writes data-pipeline and analysis code. It is decent on public benchmarks and poor on this estate: undocumented table naming, a house style for notebooks, a reconciliation step that analysts always do by hand.

  1. Define a task stream. Collect 20–40 real but non-sensitive tasks (e.g. "reconcile monthly volumes between two extracts and write a summary"). Group them by domain (finance reconciliation, operations reporting). Split them with scripts/split_tasks.py style stratified train/test partitions so some tasks are never used to improve the harness.
  2. Write an adapter. Harness² ships adapters for three benchmarks; your tasks need an equivalent that provides the task, a workspace and a place for deliverables. This is the main engineering effort and I did not see a generic adapter for custom tasks in the file tree, so check harness2/benchmarks/ and spec.py before promising a timeline.
  3. Run with k=1 first. Per task, the system runs the base harness, drafts an invariant and a domain edit, probes both, composes, and logs why. The domain edits become a visible set of reviewable files: a skill for the client naming conventions, tool guidance for the warehouse CLI, a guardrail "reopen and check every produced file".
  4. Human review of adopted harnesses. Treat the adopted harness and EXPERIENCE.md lessons as a change request. Someone who knows the client reads the diff before it goes anywhere near production.
  5. Measure on held-out tasks with client-owned acceptance checks (row counts, tie-outs, analyst rubric), comparing base vs adapted harness on the same tasks.
  6. Freeze and hand over. The deliverable to the client is the reviewed harness files and the evidence, not a live self-modifying system.
Why it matters

The pitch for an FDE: a repeatable, auditable way to turn "the agent does not understand our environment" into a set of reviewed files, with before/after numbers.

Safety

How to pilot it safely

  • Throwaway VM, no secrets. The README says executor network access is unrestricted and Codex runs with its sandbox disabled. In substrate/codex.py the reference argv includes --dangerously-bypass-approvals-and-sandbox. Use a disposable machine with no production credentials or client data mounts.
  • Network egress control at the network level. The experiments guide says to apply restrictions via an egress firewall or DNS policy, not a tool setting, because of the disabled Codex sandbox. It documents a Codex rollout on JobBench downloading its task's grading rubric from Hugging Face without being told to. For a client pilot, allow-list only the model endpoint and required package mirrors.
  • Start tiny. The README warns that model-backed runs incur API costs and suggests small task selections. Use --dry-run to preview, --max-tasks (note it caps tasks per domain) and a fresh HARNESS2_RUNS_DIR per experiment.
  • Keep held-out tasks. Compose decisions are model judgment on behavioural contrasts. The paper says these are sensitive to execution variability and shared model biases and do not guarantee correctness or transfer. harness2-judge --bases scores the base executions so you can compare.
  • Report the configuration. Executor, editor, judge, k, mode, seed and network restrictions, as the guide recommends.
  • Data governance first. Prompts, trajectories and deliverables go to whichever model provider you configure (the shipped config uses Vertex AI). Get client sign-off on that before any real data.
Why it matters

The security posture is a research-code posture. Your job is to wrap it in the controls a client InfoSec team expects.

Caveats

Risks and limits

  • No ground truth means no guarantee. The authors' own Limitations section says refinement relies on behavioural contrasts and model judgment and does not guarantee correctness or transfer to a different task.
  • Cost multiplies. Each task needs a reference run, probes, composition and a final run, plus editor sessions. The authors say they tested a bounded budget range, not an optimal allocation.
  • Benchmarks, not your estate. Results are on WorkBuddy-Bench, JobBench and LAB with Gemini 3.5 Flash and GLM-5, with Claude Opus 4.8 as the default editor. I read no result on enterprise data warehouses or client codebases. Do not quote the paper's numbers as your expected uplift.
  • Blind editing hurts. The 73.4 to 63.2 control shows that rewriting harnesses without execution evidence can make things worse. The evidence step is doing real work.
  • Library growth. The paper lists library consolidation, stale-experience revision and adaptive stopping as future work, so expect a growing library to need manual curation.
  • Maturity. The README disclaimer says this is not an officially supported Google product. The repo shows 7.3k stars when I checked (the LinkedIn post cited 2.2k), so interest is moving quickly.
  • Benchmark validity. The task data for all three benchmarks is public, hence the rubric-leak warning. Epoch also notes that customising harnesses per model risks hill-climbing on the evaluation. Keep your acceptance checks private.

For you

Consulting takeaways

  • Sell the harness as an asset. "Model plus harness" gives you a language for scoping: the model is a commodity choice; the harness captures client-specific process, guardrails and skills as reviewable files.
  • Offer a measured pilot, not a promise. Fixed task set, held-out split, base vs adapted, written-up config. That is the shape of a credible FDE engagement.
  • Process failures are the cheap wins. The paper's case study fixed verification and reconciliation habits. Ask clients where analysts do manual tie-outs: those become guardrails and scripts.
  • Use the ideas without the framework. Even if you never run Harness² you can copy the pattern by hand: compare two variants of an agent setup on the same task, keep only edits tied to an observed difference, and record the lesson.
  • Lead with controls. Egress policy, sandboxing and held-out evaluation are what unlock approval in a regulated energy environment.

Highlighted

Trend watch

Harness engineering is moving from hand-tuning to self-editing loops. The gain in this paper comes from running candidates and comparing behaviour, not from rewriting blind, and the repo itself warns about sandboxing and rubric leakage. For consultants, the durable skill is designing the evaluation and control wrapper around such loops.
